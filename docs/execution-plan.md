# BitLisp Execution Plan
## From evaluation to executable spec, measured artifacts, and hostile review

*July 26, 2026. Working plan for Evan + Claude Code (Fable 5). Companion to `bitcoin-script-successor-evaluation.md`.*

---

## Ground rules (apply to every phase)

1. **Spec before code.** No consensus-relevant behavior lands in the Python reference without a section in `/spec` it can cite. Every PR touching semantics references its spec section.
2. **Vectors are the source of truth between sessions.** Claude Code sessions are stateless; the vector corpus is not. Any behavior worth keeping becomes a vector the same day.
3. **Divergence is documented, never silent.** Anywhere BitLisp differs from CLVM, the divergence table says so and why.
4. **The novel layer gets adversarial treatment first.** The validation rules (injective output matching, mixed-tx rule, message scoping) are the only part with no external reference — they get property-based invariants and theft-bug regression vectors before feature work.
5. **Nothing in Phases 0–3 depends on the hardened-implementation language.** The language is decided ahead of the gate: C++. The independence rule stands unchanged: no Phase 0-3 artifact may assume the language.
6. **Skeleton fixed, flesh just-in-time.** Binding from day 0: the ground rules, the phase ordering and dependencies, the done-criteria, and the decision gates with their pre-registered evidence. Everything else — task lists inside phases, session specs, far-phase detail — is indicative only, and is re-planned at the recurring checkpoint when the preceding done-criterion clears. Task specs for Claude Code are written the day they're executed, against the current state of the repo. Changing the skeleton requires an explicit, recorded decision; changing the flesh requires nothing.

## Phase 3: Execution front end + language v0 + compiler

*Added 2026-07-30, decision by Evan, a recorded skeleton change under ground rule 6. The phases that followed were renumbered up by one the same day. Rationale: the Phase 4 witness measurements should come from bytecode that realistic tooling produces, not from artisanal hand-optimization. The witness-compression experiments iterate faster as compiler features than as hand-edited bytecode. And the Phase 5 hostile-review invitation is materially stronger when reviewers can write and run puzzles themselves.*

*Restructured 2026-08-09, decision by Evan, a recorded skeleton change under ground rule 6: the phase runs as serial units, execution front end before language, and the done-criterion adds the runner and the REPL. Rationale: the plan committed to a compiler but never to a human-usable execution path. Nothing in the repo takes one program, one solution, and one transaction and answers valid or invalid, with which conditions and what cost, and programs can only be born as hand-assembled bytes because no parser exists. The Phase 5 playground assumes exactly this driver without any phase building it, and bllsh sets the reviewer-facing bar: parse, evaluate, load a transaction context, step through execution. The front end is not a detour on the way to the compiler. The parser and printer are the compiler's front half, and the runner is the harness the compiler correctness story below already requires. The REPL with its stepper is table stakes rather than convenience: language ergonomics get exercised interactively there before they harden into the language reference doc.*

**Goal:** a human-usable execution front end over the Phase 2 engine, then a v0 authoring language and compiler good enough to write the four benchmark puzzles well, so every Phase 4 artifact is written in it. This is tooling, not consensus: nothing in this phase adds or changes `spec/` semantics or `python/bitlisp/` behavior.

**Serial units, in order, one per session, each landing as its own reviewed PR:**

- [x] **Unit 0, the gate at phase open: fork-vs-scratch and implementation language.** Pre-registered evidence: the dialect debt in clvm_tools and clvm_tools_rs, Rue's maturity and stability at that date, and the v0 scope below. Lean recorded 2026-07-30: our own implementation at v0 scope, with Chialisp and Rue read freely as design references under the reference-material policy (copying code in stays prohibited, influence disclosed in commit messages). Python is the default implementation language: it keeps one toolchain, and it lets the Phase 5 playground run the real compiler and the real reference VM in the browser under Pyodide. The gate decision covers the whole phase, front end included, since the parser and printer it opens with are the compiler's front half. **Decided 2026-08-10 (decision by Evan): scratch, in Python, confirming the lean.** The evidence snapshot at the decision date, from fresh clones of both toolchains. clvm_tools (Python) has been frozen as a compiler since July 2022, when its `run` command began delegating to the Rust implementation with no fallback, and it ships no REPL and no stepper. clvm_tools_rs (renamed chialisp upstream) is active but effectively single-author, about 34,500 non-test lines of Rust, with nine versioned dialect sigils threaded through the compiler as behavior toggles, two coexisting compiler paths (a 10,379-line classic port and a 21,513-line modern compiler), preserved-bug compatibility flags (a CSE dominance bug and an integer-conversion bug kept reproducible for older dialects), and a non-optional BLS dependency. Rue stood at 0.10.0 (released 2026-07-26), pre-1.0, single-maintainer, with no stability commitment and no known mainnet deployment, its builtins coupled to Chia's BLS and coin-id model. That dated snapshot also serves the typed v1 gate after Phase 5. The analysis that carried the decision: a Chialisp-class compiler touches conditions only as constant data, so BitLisp's heavily modified condition layer does not raise the cost of forking, it lowers the value, because the condition-facing units (the runner, the REPL transaction context, the benchmark puzzles) are scratch under either path and a fork would cover only the language units minus the operator table, the serializer, the embedded VM, and the constants, which must be ours regardless. The compiler must run the reference VM in-process, for `defconst`-style compile-time evaluation and for the compile-and-run test mandate, and the reference VM exists only in Python, which also keeps the Phase 5 playground a single Pyodide runtime (the package is pure Python, verified at the decision date). C++ was weighed for the compiler and declined: it would reintroduce a subprocess seam to the Python VM, roughly double the reviewed line count, add an Emscripten toolchain beside Pyodide, and couple tooling to the Phase 6 language against ground rule 5. Bitcoin Core practices the same split, C++ where consensus parses attacker bytes, Python for its test and tooling layer, and Core merged the miniscript core while leaving the miniscript policy compiler out of tree, the same authoring-side boundary this phase keeps. Scale calibration recorded with the decision: bllsh is a full front end with a stepping debugger in 3,237 lines of Python, the original Python clvm_tools toolchain is under 3,700 lines, sipa's miniscript policy compiler is about 1,000 lines of C++, so the whole Phase 3 deliverable is expected in the 3,000 to 5,000 line band, with the 21,500-line modern Chialisp compiler an outlier explained by the optimizer framework and dialect ladder we are explicitly not building. Pre-registered overturn condition: if a Phase 4 vbyte threshold is missed by compiled output, cleared by hand-optimization, and the gap traces to optimization infrastructure rather than a fixable codegen choice, the typed v1 gate reopens the fork question with that evidence in hand. The upstream toolchains stay design references under the reference-material policy, and bllsh, which publishes no license file, stays read-only in exactly the way that policy already requires.
- [x] **Unit 1: parser and printer.** Text s-expressions to program trees and back, operator names per `VM.md`, round-trip property tests, and re-serialization pinned against programs from the existing vector corpus. Landed as the assembler and disassembler in `python/bitlisp_tools/`, with the syntax stated in `docs/lang/syntax.md`. Three syntax decisions by Evan, 2026-08-10, are recorded there: unknown bare symbols are rejected rather than becoming their own name bytes and the decimal display window is wider than clvm_tools' two bytes, the two marked clvm_tools deviations, plus string display checked before decimal, an ordering forced by the wider decimal window (clvm_tools' two-byte window never overlaps its string floor, so it has no such ordering to deviate from). The decimal window was refined 2026-08-11 (decision by Evan, during PR 46 review): sign-split, eight bytes for non-negative minimal encodings and two bytes for negative, because half of random binary atoms lead with a byte of 0x80 or above and a symmetric window printed them as plausible negative integers. The analysis that carried it: display cannot recover intent from bytes (identical atoms have identical spellings available), so the window is set where a genuine number is the likely reading, and hex, which is never misleading, covers the rest.
- [x] **Unit 2: single-spend runner.** One command takes a program, a solution, and a transaction context, runs evaluation, condition parsing, and full validation, and reports the verdict, the emitted conditions, and the cost, or the error. Accepts text s-expressions from unit 1 or raw bytecode, and takes the transaction context in the validation corpus's shape. Condition output is rendered schema-aware (added 2026-08-11, decision by Evan): each operand prints by the shape `CONDITIONS.md` declares for it, amounts and heights as decimals, hashes and scripts as hex, so the display needs no byte-length guessing where the spec already knows the type. **Landed as the `bitlisp-run` console script over a runner library in `python/bitlisp_tools/`.** Two surface decisions by Evan, 2026-08-14: the argument conventions follow clvm_tools' brun (program and solution are file-or-literal positionals, one `--hex` flag switches both to raw serialized bytecode, an omitted solution is nil, and the cost budget defaults to brun's 11,000,000,000), and the command ships as the repo's first pip console script, matching how Chia distributes brun, rather than as a `tools/` script. The line the surface keeps: text and hex never auto-detect, because the same digits are valid as both, while brun's file-or-literal fallback is adopted with its rare shadowing case accepted for familiarity. Exit codes draw the consensus boundary: an invalid spend exits 1 with the pinned error code, including bytecode that fails strict deserialization, and authoring-side input that never existed as bytes exits 2. A corpus replay test pins the runner to the validation vectors' own verdicts by re-running each carried condition list as a quoted program.
- [x] **Unit 3: REPL with stepper.** Interactive evaluation with the unit 2 transaction context loadable, a definitions scratch space, and a debugger: step, step-over, continue, trace. bllsh's command set is the reference point. From unit 4 onward this is the surface where language ergonomics are played with before they harden. Folded in from the clvm_tools parity check (2026-08-14, decision by Evan): companion one-shot commands that assemble text to bytecode hex and disassemble hex back to text, the opc and opd equivalents, thin wrappers over the unit 1 library beside `bitlisp-run`. **Landed as the `bitlisp` REPL over a pausable debug machine in `python/bitlisp_tools/`, with `bitlisp-asm` and `bitlisp-disasm` beside it.** Three decisions by Evan, 2026-08-14. First, the stepper seam: a standalone debug machine in the tools package, reusing the consensus operator table and cost constants and reimplementing only the control loop with explicit state, `machine.py` untouched, pinned to `machine.run` by differential tests over the VM vector corpus and hypothesis-generated programs. This is the pattern of cldb in clvm_tools_rs, a stepping interpreter beside a hookless consensus runtime, chosen over clvm's `pre_eval_f` callback, which inverts control and never grew into an interactive debugger, and over a generator refactor of the consensus loop, which would reshape the most scrutinized file in the repo to serve tooling. Second, the names: `bitlisp-asm` and `bitlisp-disasm` after the library functions they wrap, and the bare `bitlisp` name for the REPL, the toolchain's front door, following bllsh's eponymous precedent. Third, definitions are constants only: a binding resolves a bare name to a parsed node exactly where the reader would otherwise reject an unknown symbol, so a binding can never change the meaning of text that already parses, and parameterized functions wait for the unit 4 compiler that owns call semantics. Surface details recorded with the landing: the debugger vocabulary is `step`, `next`, `cont`, `trace`, and `abort`, with step-over and continue as the concept names. The converters exit 0 or 2 only, exit 1 staying reserved for a spend verdict, with the pinned error code kept in the message on strict-deserialization failures. Every node the REPL displays passes through one rendering seam, the hook the unit 4 symbol table consumes. Step-over is a stack-depth predicate, run until the task stack is one shorter than before the pending task ran, well defined because apply frames sit under their arguments' evaluation frames.
- [x] **Unit 4: language core.** Named functions, constants, condition constants matching `CONDITIONS.md`, native `sha256tree` emission, compilation to bytecode, and compile-and-run tests against the reference VM. New constructs become usable in the REPL the same session they land. The compiler also emits a symbol table mapping compiled names to bytecode positions, and the unit 3 stepper consumes it, so stepping through compiled code shows source names rather than raw bytecode. Added 2026-08-14 from the clvm_tools parity check (its .SYM emission is what makes its debugger usable on compiled output), pinned here so the capability is designed in rather than bolted on. **Landed as the compiler in `python/bitlisp_tools/compiler.py`, the `bitlisp-compile` console script, and the REPL's language surface, with the language stated in `docs/lang/language.md`.** Four decisions by Evan, 2026-08-15, taken after reference studies of clvm_tools, clvm_tools_rs, and bllsh. First, the module form is named `program`, after the repo's own vocabulary for the artifact it compiles to, with Chialisp's `mod` bridged in the glossary. Second, the special forms `if` and `list` ship in this unit as compiler forms rather than waiting for the macros unit: the VM's `i` is eager, so `if` compiles to the `(a (i C (q . T) (q . E)) 1)` idiom recursion terminates through, and `list` folds into `c` so condition output is writable, with bllsh's compile-to-nothing `report` weighed and declined because the stepper already provides that visibility. Third, the symbol table keys on the tree hash of each compiled function body, refining this bullet's earlier "bytecode positions" wording, which nothing at display time could look up: the stepper holds live nodes rather than offsets, a hash survives serialization so a symbol file accompanies compiled hex across sessions, and clvm_tools' main.sym and cldb key the same way. Fourth, the REPL accepts source forms at the prompt, `defun` and `defconstant` lines declaring directly, and eval, spend, and debug retry their text as language source exactly when the reader rejects it on an unknown name, so raw VM text never changes meaning and the language reference's examples paste as written. Design points recorded with the landing: the compiled environment is (function tree . args) with calls passing the tree along, the Chialisp layout unit 5 currying expects, and a function-free body emits bare. Constants inline as quoted literals and never enter the environment tree, so compilation needs no optimizer, output carries no constant-folding pass at all, and only pairs carry symbol-table keys, which closes upstream's value-keyed collision (any atom 51 tracing as CREATE_COIN). The function tree orders by declaration rather than alphabetically, unreachable definitions prune, call arity is checked at compile time, `defconstant` is literal-only with the constexpr `defconst` declined, and declarations, `def` bindings, condition constants, and reserved words share one namespace. The debugger alone consults the symbol map, showing a matched body as its name with live arguments by parameter name, while disasm, compile output, and results print canonical text, so the round-trip guarantee stays intact. Compiled representatives are pinned in `vectors/vm/compiled-programs.json` per ground rule 2.
- [ ] **Unit 5: currying and program identity.** Added 2026-08-15, decision by Evan, a recorded skeleton change under ground rule 6, from the comparative review against bllsh and clvm_tools: `curry` and `uncurry` as library and command surfaces, plus a flag on the converters printing a program's sha256 tree hash, the clvm_tools `opc -H` equivalent. Curry bakes chosen arguments into a program and yields a new program with the rest of the solution still open, uncurry recovers the template program and the baked arguments by structural match, and together with the tree hash they are how Chia's deployed coin ecosystem names and verifies program families: a wrapper is recognized by uncurrying it and tree-hashing the template. The unit 7 benchmark puzzles consume all three, the singleton wrapper most directly. A discrete unit rather than a fold into unit 4, because none of it touches the compiler's call semantics, and split out of the macros unit where currying helpers first sat, because currying operates on programs rather than on source text. The tree-hash flag stays distinct from the Phase 4 commitment-hash utility on purpose: a program's own tree hash is already defined by `sha256tree`, while what a scriptPubKey commits to waits on the commitment scheme, so that deferral stands unchanged.
- [ ] **Unit 6: macros and includes.** Currying helpers moved to unit 5, 2026-08-15.
- [ ] **Unit 7: the four benchmark puzzles, written in the language, as the acceptance artifact:** payment pool (benchmark 3), async offer (benchmark 6), vault, singleton wrapper. This phase makes them exist and run. Phase 4 measures them. One PR per puzzle where the size warrants it.

**Standing constraints, unchanged from the phase's creation:**

- **Hard scope boundary.** v0 is a small s-expression language with Chialisp-class ergonomics: function definitions, macros, constants, includes, currying helpers. BitLisp-native from day one, no BLS vocabulary. Explicitly out of v0 scope: static types, a Rue-class frontend, editor tooling, optimization beyond the obvious. The typed v1 question is a separate gate after Phase 5 review, informed by Rue's maturity at that date. One benefit recorded for that gate's ledger (2026-08-11): a checked type system would let the REPL print results by known type instead of by byte-length heuristic, the one display surface types can actually reach, since compilation erases types from bytecode and foreign bytecode never has them.
- **Compiler correctness story.** The compiler is not consensus code and sits outside spec-before-code, but compiler bugs become fund-loss bugs for users. Every language construct gets compile-and-run tests against the Python reference VM, and every compiled benchmark puzzle is pinned as a vector the same day, per ground rule 2.

The stopgap never enters the tree, and the plan bends instead of breaking. The fallback covers the language units only: the front end (units 1 to 3) has no off-tree substitute and does not slip out of the phase.
